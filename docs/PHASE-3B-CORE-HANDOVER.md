## Core data and history contracts

**Identity:** children.id is a server-generated random UUID. student_id is its permanent uppercase, printable UUID representation, generated by PostgreSQL and unique. There is no invented CAC prefix, sequence range, year encoding or source ID. Database-generated columns and immutable identity triggers prohibit replacement; transfers never regenerate it. This nonsemantic technical representation can be reviewed for usability; any future friendly alias needs an approved separate design rather than silently changing permanent IDs. New-registration RPCs allocate identities; names never act as uniqueness/matching keys. Same-name synthetic registrations stay distinct. No historical identity resolution or external-ID issuing scope is invented.

**Profiles:** only full name, controlled Girl/Boy gender and nullable Class-10 board-result projection are modeled. No DOB, phone, guardians, household survey, financial/safeguarding notes or free-text challenge field. Private-profile reads require an explicit can_read_profiles grant in addition to verified teacher/officer centre scope; Leadership gets programme IDs without names. Registration can capture the minimal name, but profile corrections/board-result editing are not implemented. Their field-level rights and history/date semantics need review before an adapter is built.

**History:** enrolments store explicit starts_on and exclusive ends_before with grade 1–10, Morning/Evening and existing Active/CAC dropout/Left programme vocabulary. Dates are supplied, never invented from grid/year/row position. Non-Active episodes require an explicit end. Grade/shift/centre changes add episodes; the prior assignment cannot be retagged. A closure cannot invalidate already recorded attendance, results or participation. Composite FKs preserve the original child/centre/shift/enrolment context on every dated fact. Shared enrolment locks serialize facts against closure. Closure is first-close only; correcting/reopening a closed episode requires a reviewed follow-up design.

The exclusive end is an explicit storage convention, **not approval of converting a frontend exit date**. Multi-centre/shift overlap policy remains unresolved: no blanket overlap ban or inferred transfer is imposed. Exact duplicate episodes are rejected. Moving a known child requires write authority over an existing linked centre and the destination; a receiving-only operator cannot claim someone else's identity through a transfer API. A coordinated verified transfer workflow remains a product/security decision.

**Academic years/results:** academic-year start must be April 1 and the stored exclusive end is next April 1. Quarters 1–4 cover Apr–Jun, Jul–Sep, Oct–Dec, Jan–Mar; admins supply reference rows without fabricating assessment occurrences. Missing result is no accepted result row, never zero/Absent. Zero is valid. Dates must lie inside the approved quarter and verified enrolment. Current max is exactly 25, score range 0..25, one accepted child/definition result; corrections create revisions, not routine attempts. Numeric storage preserves possible decimals without selecting a final precision/rounding policy. Historical max100, unknown years/dates and Q-to-F aliases are not normalized or imported. Additional papers/scales/exceptional repeats require another approved design.

**Attendance:** statuses are P Present, A Absent, L Leave, WO Sunday, MM Monthly Meeting. Summary returns raw counts and 100*P/(P+A+L), with NULL for zero denominator; it does not round or apply unapproved bands. No missing marks become A. cac_sessions is a minimal explicit confirmation calendar, **not evidence of Held/Cancelled delivery**. Confirmed non-scheduled entries are holidays; absence of a calendar row proves nothing. P/A/L on a confirmed holiday is rejected; a conflicting holiday cannot be inserted over those marks. Advisory date/scope locks serialize those checks. WO/MM and confirmed holidays do not enter the percentage. excluded_count counts recorded excluded occurrences, not all possible holiday student-days. No complete-calendar/unknown-day coverage claim is made. H, holiday reason vocabulary, authoritative calendar process, dropout/engagement thresholds and display rounding remain pending.

**Activities:** staff explicitly supply the event ID (idempotency identity), name, centre, shift and date. Participation is true/false/NULL, unique per event/child, tied to a matching verified enrolment and event date. No activity catalogue, category, Held status, alternate-Saturday pattern, exactly-four constraint or synthetic historic event bridge. Both-shifts events and scope/date corrections need a later contract. Historical monthly slot responses remain outside operational events and await separately authorized history-table/import work.

**Morarji:** programme_cohorts is used only for this Morarji scope at present; no other programme is activated. Cohort labels/year links must be supplied explicitly, never derived from missing source dates. Membership is unique cohort/child with verified centre/enrolment linkage. Only nullable applied/attended/passed and source-backed school text exist. No inferred exam/training-day interpretation, admission/selection/scholarship flag or flag-implication constraint. Genuine conflicting/unverified source records remain held in restricted foundation exceptions, not promoted by this code.

## Security and mutation boundary

mass_core and mass_foundation are private; only the curated mass_api schema is exposed in the isolated API test. No hosted exposure settings were changed. All 17 core tables have enabled and forced RLS. Authenticated reads use server-owned, time-valid user_scope_grants; empty/unverified/expired grants give no programme access. Each Cluster Officer's operational scope is a verified list of centres, not an inferred cluster/name mapping. Leadership reads only its explicitly granted centre scope and cannot write. As a conservative guard, an active Leadership designation prevents writes even if an accidental second business-role grant exists.

No actual grants/accounts/memberships are installed. mass_core_admin is non-login and can maintain reference metadata and verified scope grants (including ending a grant); no public scope-management RPC exists. Role labels/JWT business-centre claims do not grant database access. Admin identity verification and production grant/revoke authority still require approval. Scope is evaluated at request time; actual historical-read entitlement and private disclosures require production review before real users are granted rights.

Authenticated has SELECT privileges with RLS, but no direct table mutation privileges. Typed security-definer RPCs check the authenticated principal and source/destination centre before writing; centred tables also enforce owner INSERT/UPDATE scope policies. Audit/constraint helpers use fixed pg_catalog search paths, qualified objects, non-login non-bypass owners and no PUBLIC execute. Private owner SELECT policies exist for bounded authorization/constraint helpers; no generic owner SQL/JSON execution endpoint is exposed. anon/service_role receive no schema/table/helper grants. BYPASSRLS is not a substitute for table/schema ACLs.

Write RPCs lock existing rows and enforce expected revisions: expected=0 means create only; otherwise the exact existing row_version is required. Stale calls raise **PT409**, mapped by PostgREST to HTTP 409. This is a logical edit conflict, not retryable PostgreSQL serialization_failure; tests caught and removed the resulting HTTP retry behavior. Identity, fact scope/date and event context are immutable; scalar correction fields alone can change. Clears, deletes, profile correction, assignment reopening and general offline/bulk workflows are intentionally not exposed yet.

**Audit:** a forward migration adds optional actor_user_id -> auth.users to the original private audit relation and extends its entity allowlist. Core writes record actual database principal/role, trusted request UID, entity UUID/type, operation/time and revision-only metadata. No name, score value, school text, raw SQL/request or before/after personal payload enters audit metadata. Writes and audit append are atomic; append failure aborts registration. Operation/revision history is attributable, but is **not a recoverable before/after business-value archive**. Any such private revision-store requirement needs a retention/correction design. Existing foundation ingestion/review remains technical database-principal attribution; no staff exception-review API is introduced. Auth-user FKs restrict deletion until a reviewed deprovisioning/retention process exists. No retention period or automatic deletion policy is selected.

```sh
bash tests/foundation/run-local.sh
MASS_TEST_REST=1 bash tests/core/run-local.sh
npm run check
npm run build
```

The foundation runner is now limited to migrations 1–6 so its original regression suite remains independently reproducible. The core runner applies all 15 in order to a fresh database and creates test-only Auth stubs/principals. Neither runner accepts DATABASE_URL, existing project/database, private workbooks or real fixtures. The core database, PostgREST and disposable Python HTTP client share an **internal Docker network with no published ports or host-data mounts**. Database storage is temporary memory; containers/network are removed on exit. The optional API signing secret is generated at runtime, never committed/logged. It is solely a synthetic issuer; real GoTrue is not running. Images are digest-pinned. MASS_TEST_REST=0 runs SQL-only and is not an API compatibility result.
