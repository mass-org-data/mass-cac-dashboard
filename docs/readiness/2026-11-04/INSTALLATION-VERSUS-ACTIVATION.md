# Default-disabled installation proposal

This review supersedes the automatic-capability-exposure concern in OPERATIONAL-ACTIVATION.md. It is a prepared and locally tested change, **not an applied hosted release**. The READY Preview confirmed by MASS remains commit 86afb31d. Existing development/calculation/parity evidence is retained; no redesign or workbook audit was repeated.

## What was implemented

- Private `mass_activation` schema with two technical relations: `features` (14 default-false controls) and immutable `events` (opaque approval reference, feature/state, timestamp and database principal). Both force RLS. No schema/table/function access is granted to authenticated, anon or service_role in this private schema. No staff account, centre assignment or scope grant is created or changed.
- A fixed-search-path owner function returns a feature Boolean only for an authenticated subject; a narrowly granted helper raises SQLSTATE42501 when disabled. There is no browser-facing activation endpoint. Enabling a feature requires separately authorized trusted database administration, a nonempty opaque approval reference and a logged update.
- The seal adds one checked entry guard to each of **21 existing/new RPCs**, including nested primitive writes and proposal024. It retains the original owner, ACL, signature, volatility, SECURITY mode, search_path and calculation/validation body. Unclassified API functions cause installation to stop. Repeated sealing verifies the expected existing guard. The original RLS checks and business validation still run after an enabled gate; a flag never grants a centre or profile capability.
- Attendance, assessment and visit entry are separate from corrections. expected=0 cannot overwrite an existing row because original version/identity constraints still apply. Batches check the global entry gate then each row's entry/correction gate in the same transaction. The frontend skips already-equal attendance marks and keeps existing assessment values read-only during entry-only operation; genuine corrections remain blocked. A forbidden row rolls the whole batch back.
- Historical corrections, transfers, profiles, enrolment changes, calendar changes, activities and Morarji writes are **hard-off by CHECK constraint**, not simply unchecked feature flags. Their less granular write endpoints can change prior records, so they remain unavailable under the current preservation requirement. Changing this constraint or those write semantics requires a separate reviewed change; no new business rule is inferred.
- Registration remains default-disabled; no new student registration is authorized by this work. `reviewed_reads` is default-disabled independently of operational writes and controls proposal024. All initial feature values are false.
- Frontend capability detection separates installed read support from versioned explicit write authorization. Missing/legacy/unrecognized activation metadata cannot enable writes. Original controls, charts, forms, filters, layout and downloads remain; unavailable entry controls report activation pending without an RPC mutation. Save Attendance and scoped history are read-only and remain available where supported. Old deployed clients may still show forms, but direct API guards protect the database regardless.

The activation registry is supplementary technical infrastructure, not a replacement programme data model. Scope grants and ACLs stay unchanged; withholding operations through the new gate is an intentional runtime restriction. Existing baseline write RPCs are also sealed to avoid an alternate unguarded route around the new endpoints.

   `python scripts/activation/prepare.py --output /private/reviewed-installation`
   This produces exactly four envelopes,020→021→022→023. It never opens a database connection or includes024 by default. Output stays outside the checkout. Review `ENVELOPES.json`; it identifies each untouched source hash and its distinct execution-envelope hash.
3. Each envelope contains one executable BEGIN/COMMIT transaction (recorded SQL strings in the ledger are data), a bounded lock/statement timeout, migration advisory lock, expected ledger/count checks, canonical stage SQL, and the seal **before COMMIT**.020 creates the private control plane inside this same transaction. Stage DDL, entry guards, capabilities and the real ledger insert commit together. There is no interval where a separately committed unguarded RPC is visible. Do not run the canonical files bare and then install the gate afterward.
4. The chosen executor must be separately authorized and proven against the actual managed environment. Membership catalog evidence is not executed DDL proof. Required controls are more than checksum validity: expected baseline definitions, actual ledger columns/privileges, owner roles, existing API exposure and absence of conflicting custom objects must be verified. The builder accepts the reviewed baseline names/018–019 versions, including historical provider aliases, and stops on unexpected ledger state.
5. Execute one approved envelope at a time with error-stop. After each commit verify canonical original-column data fingerprints, grants, ACLs/owners, RLS and every write guard; compare the ledger's recorded canonical-plus-control/seal statements and envelope manifest. New technical control rows are expected; original grants and programme records are not changed. On failure stop, roll back an open transaction and reconcile; retain earlier successful stages. No reset, down migration, DROP cleanup, manual ledger stamping or automatic retry.
6. All writes remain disabled after installation. New backend code need not be active merely because it exists. Gates prevent subsequent invocations; they do not cancel already-running calls or undo committed writes. Confirm/drain in-flight application writes during the controlled cutover window without pausing Vercel, disconnecting GitHub or changing staff grants. Verify actual managed authenticated read loading, unchanged original values and HTTP403/42501 for disabled endpoints through a reviewed safe probe. Deliberately invalid all-NULL probes were used **only in isolation**; do not transplant them into production if a gate might be missing. Hosted verification should inspect all guarded definitions/ACLs first, use read-only capability checks, and reserve mutation-negative execution for a safe authorized environment.
7. Review024 separately; it remains a proposal. `--include-proposal-024` produces an additional clearly labeled **proposal** envelope for isolated review, not implicit deployment authorization or formal promotion. A production promotion must freeze a final unique migration identity/hash and rerun affected checks. Installation seals its function and advertises no reviewed_charts capability until reviewed_reads is explicitly approved/enabled. Validate its actual scoped read results before operational flags.
8. Only after the private grant audit and separately authorized operator/scope review may genuine attendance/assessment/visit **new-observation inserts** be considered for activation. A flag change is logged and requires an opaque approval reference. Capture the exact operator scope and source evidence; do not fabricate observations to pass tests. Staff provisioning and Google Sign-In remain prohibited. Historical correction/transfer toggles are not available under this proposal.

Default-off installation does not require requesting a personal backup from MASS. It does require authorization for the new control-plane patch and deliberate temporary blocking of baseline writes, a controlled execution window and actual managed privilege verification. Function/trigger/constraint replacement and table locks still make installation a real hosted change. Transaction rollback protects an uncommitted installation; it does not reverse later committed programme edits. Without a verified recovery point, destructive changes, existing-value overwrites and unsafe corrective replay remain held. No new paid infrastructure is proposed.
