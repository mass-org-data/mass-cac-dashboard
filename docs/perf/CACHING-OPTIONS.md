# Caching options for the MASS dashboard: assessment and recommendation (14 November 2026)

Status: analysis only, nothing implemented. Recorded as a pending task in `AGENTS.md`.

## What we measured and learned first
- **Where the time goes.** The first screen of the Overview needs 8 requests; the slow parts are the heavy `reviewed_chart_metrics` reports (mean 865 ms on Production, up to 8 s under load) and, on the Annual donor summary, eight of them in a row (10 to 14 s). Page delivery (Vercel CDN and network) adds little: the deployed Overview was within noise of the same build served locally.
- **The database already caches pages.** The preview database is 153 MB with `shared_buffers` 224 MB and a 100 percent buffer cache hit ratio, so the data is entirely in memory. The heavy reports are CPU work (aggregating about 200,000 attendance rows), not disk reads. Result: caching the *answers* (not the data pages) is what would help. The slow "first load after idle" (4.5 to 5.2 s requests seen twice) is not a disk-cache effect; its cause (for example shared-CPU burst limits on a small compute size) is unconfirmed and should be checked in the Supabase metrics.
- **What Vercel serves today.** Static files only. Checked on the deployed preview: `cache-control: public, max-age=0, must-revalidate`, `x-vercel-cache: HIT`, Brotli compression. The main script is 705 KB raw, 201 KB over the wire. Because `max-age=0`, the browser re-checks every file on every visit (a conditional request per file) even though the file names are content-hashed and can never change. All programme data goes from the browser straight to Supabase, so Vercel never sees or can cache it.
- **What the app already caches (in memory, per page visit):** the Overview reports and series (`createOverviewService`), student rosters per centre (profiles service). Nothing is shared between screens or kept when you leave a screen; for example Attendance and Assessments ask for the same all-centre report the Overview just loaded.

## The options, with pros and cons

| # | Where | What it is | Pros | Cons and risks | Effort |
|---|---|---|---|---|---|
| 1 | **Vercel CDN: static asset headers** | Add `Cache-Control: public, max-age=31536000, immutable` for the hashed `/assets/*` files in `vercel.json`; keep `index.html` revalidating. | Repeat visits and reloads skip re-checking about 220 KB of hashed files; no data involved so no privacy risk; reversible in one line. | Gains only the static files (the data fetch dominates); a wrong rule on a non-hashed file would serve stale code, so apply it to `/assets/*` only. | Minutes |
| 2 | **Vercel: caching API responses** (functions with `s-maxage`, Runtime Cache, Edge Config, KV) | Put a Vercel function between the browser and Supabase and cache its answers. | Shared cache across users in the same scope. | Our data is private and per-scope: a shared cache means a cache-key and authorization layer we would have to build and keep correct, any mistake leaks student data across users; adds a network hop and a second place for secrets; the browser currently talks to Supabase directly with only the publishable key. Edge Config and KV suit configuration and flags, not 200,000-row aggregates. | High, and risky. **Not recommended.** (I could not verify the details of Vercel's Runtime Cache from its docs, so this rests on the architecture, not on that product.) |
| 3 | **Browser: in-memory server-state cache (React Query / TanStack Query)** | One cache inside the React app keyed by user, role, screen and filters, with a freshness time per kind of data, shared by all screens. | Revisiting a screen or moving between screens becomes instant; Attendance, Assessments, Morarji and the Annual summary reuse the reports already loaded; duplicate requests collapse into one; stale data shows while a fresh copy loads; automatic retry (helps the occasional cold timeout); fewer database calls overall, which also lowers the chance of statement timeouts. Fits the existing service layer (the services are already pure functions of `rpc`). | Does not speed up the very first load of a screen; stale-data risk after writes unless every save invalidates the right keys (attendance, assessment, profile, visit saves each need a rule); must be cleared on sign-out, role switch and when the 30-second scope check changes the scope, and keyed by user and role so one account can never see another's data; adds a library (about 13 KB). Keep it **in memory only**. | Medium (a few days with tests) |
| 3b | Hand-built React store (Context or Redux) | Same idea written by hand. | No new dependency. | Re-implements freshness, de-duplication, retries, cancellation and invalidation, which is where the bugs are. Not recommended over option 3. | Medium to high |
| 4 | **Browser: persistent cache** (`localStorage`, IndexedDB, service worker caching API calls) | Keep answers on the device across visits. | Instant return visits. | Student records would sit on shared or lost devices after sign-out; stale answers after another user saved; hard to guarantee clearing. **Not recommended** for programme data; fine only for non-sensitive static files (see option 1). | Medium |
| 5 | **Browser HTTP cache of Supabase responses** | Make the database API send `Cache-Control` (PostgREST can set response headers from a pre-request function, and `rpc` calls can use GET). | Free for the browser to reuse repeated identical calls. | The cache key is the URL, not the signed-in user: if two accounts use one browser the second could be served the first one's answer unless every response varies on the credential; hard to prove safe. Not recommended. | Medium, risky |
| 6 | **Database: precomputed summaries** (summary table or materialized view, refreshed by triggers or `pg_cron`) | Keep monthly attendance totals (present, absent, leave, excluded) per centre, shift, grade and gender, and assessment counts per round, up to date; `reviewed_chart_metrics` and friends read the small summary instead of scanning 200,000 rows. | The real fix for slow first loads and the Annual summary (a report that takes about 1 s would take milliseconds); helps every user including the very first; works whatever the browser or device; scope checks stay inside the existing guarded functions; `pg_cron` and `pg_prewarm` are available in Supabase. | Must reproduce the approved calculations exactly (we have the 1,440 plus 63 parity cases as a safety net); a saved attendance must show immediately (so update on save, or refresh the affected centre and month, not only on a schedule); new tables, triggers and a reviewed migration; Production must receive it through a gated release (it does not get anything today); more to maintain when a rule changes. | High (about one to two weeks with parity tests) |
| 7 | **Database: a batched annual function** | Like the monthly series: one call instead of eight monthly reports for the Annual donor summary. | Cuts that page from about 10 to 14 s to roughly the cost of one report; small and low risk; same pattern we already proved. | Only helps that page; still scans the data each time. | Low to medium (a few days) |
| 8 | **Database: compute and keep-warm** | A larger compute size, or a scheduled light query so the instance is not idle. | Immediate, no code; may remove the slow first-after-idle request if that is CPU burst limits. | Costs money; does not reduce the work per report; the cause is unconfirmed (check the Supabase CPU graphs first). | Low (a setting), after a measurement |
| 9 | **External cache (Redis, Upstash)** | A cache next to the database for computed answers. | Fast shared cache. | A new service, secrets and invalidation, and the same cross-user caution as option 2. Option 6 gives the same benefit inside the database. Not recommended unless 6 falls short. | High |

## Recommendation
Work from cheapest and safest to most valuable, measuring after each step (use `scripts/perf/overview-react.mjs` and `scripts/perf/pages-react.mjs`):

1. **Now (minutes, no risk): option 1**, immutable headers for `/assets/*`. Also split the big script so a screen loads only its own code (the 705 KB bundle is one chunk today).
2. **Next (days): option 3 plus option 7.** Add TanStack Query as an in-memory cache with per-user and per-role keys, cleared on sign-out, role change and scope change, never persisted; reference data (years, cohorts, directory) fresh for the whole session, reports for a few minutes, registers always revalidated, every save invalidating its keys; prefetch the next likely screen when idle. Add the batched annual function. This fixes screen-to-screen speed and the slowest page without touching how the numbers are calculated.
3. **Then (one to two weeks, only if the first loads are still too slow): option 6**, the database summaries, as a reviewed migration with parity tests, applied to the preview first and to Production only through a gated release. This is the lever that removes the cost of the first load for everyone.
4. **In parallel (cheap): option 8**, but only after looking at the Supabase CPU and connection graphs to confirm what the slow first request actually is.
5. **Do not do:** options 2, 4, 5 and 9 for programme data. The data is private, scoped per user and role, and the strongest caches for it are the ones that live in the browser's memory or inside the database where the permission rules already are.

The two things to settle with the owner before starting step 2: how stale a number may be on screen (for example, is a report that is up to five minutes old acceptable on the Overview, given that saves refresh it immediately) and whether Production is allowed another database release for step 3.

## Sources
- Vercel, [Cache-Control headers](https://vercel.com/docs/caching/cache-control-headers) and [CDN cache](https://vercel.com/docs/caching/cdn-cache): static files are cached on the CDN by default; hashed assets are normally served `max-age=31536000, immutable`; headers can be set in `vercel.json`.
- PostgREST, [transactions and response headers](https://docs.postgrest.org/en/v14/references/transactions.html), and Supabase, [securing your API](https://supabase.com/docs/guides/api/securing-your-api): a pre-request function can set response headers such as `Cache-Control`.
- TanStack Query, [important defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults): `staleTime`, `gcTime`, invalidation; persistence is opt-in.
- Measurements in this repository: `docs/perf/DEPLOYED-OVERVIEW-RESULT.md`, `PHASE-5-ANNUAL-DONOR-RESULT.md`, response headers and database size read from the deployed preview and the preview project on 14 November 2026.
